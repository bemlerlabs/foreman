## 1) Das Plugin-Subsystem in ephe (Beweislage)
- **Dokumentation:** `docs/PLUGINS.md` (Manifest-Spec v1, Enforcement-Semantik), `docs/PLUGIN_SDK.md` (Autoren-Einstieg: Ordner anlegen → `ephe plugin list` → REST-Check), `docs/PLUGINS_OVERVIEW.md`, `docs/PLUGIN_PLATFORM_P1/` (Plattform-Roadmap), `docs/SKILL_PACKS.md`, `docs/DISCOVER_MARKETPLACE_DESIGN.md`.
- **Code:** `core/plugin_manifest.py` (Validierung), `core/plugin_store.py`/`plugin_registry.py` (Scan/Registry), `core/plugin_runtime.py` (Gating), `core/plugin_commands.py` (Slash-Menü), `core/plugin_install.py` (ZIP-Install mit Zip-Slip-Guard), `core/plugin_listing.py`/`plugin_admin.py` (REST `GET /api/plugins`, `/api/plugins/commands` auf :8765), `core/plugin_signing.py` (First-Party-Signaturen, Key `plugins/first-party.pub.pem`), `core/skills.py` (Skill-Ladepfade), `core/user_hooks.py` (User-Hooks, getrennt vom Plugin-Manifest).
- **Verzeichnis-/Ladekonvention:** Plugin = Verzeichnis `~/.ephe/plugins/<name>/` mit Pflicht-Manifest `ephe-plugin.json` (`manifest_version: 1`; `name` = Slug = Ordnername; Semver; `permissions.tool_families` ⊆ {read, write, shell, network, memory, vision, docs, browser}; `data_roots` nur Deklaration). Fail-closed: ein Regelverstoß quarantänisiert das ganze Plugin (sichtbar als Fehler in `GET /api/plugins`); Scan ist fail-soft pro Ordner. Enable/Disable über Registry steuert ab dem nächsten Turn — kein Neustart. User-Skills zusätzlich in `~/.ephe/skills/` (user skills haben Vorrang vor built-in `skills/`, Deaktivierung über `skills_state.json`).
- **Komponenten, die ein Plugin melden KANN:** `components.skills` (Skill-Packs `skills/<id>/SKILL.md`, agentskills-artiges Frontmatter: name/version/trigger/description/when_to_use/when_not_to_use/tools+allowed_tools/artifact_types + System-Prompt-Abschnitt), `components.commands` (`{name, description, template?}` → `/name` im Composer, Template-Expansion serverseitig), `components.agents` (Helfer-Agent-Profile, `tools ⊆ TOOL_MAP`, Unbekannter Tool-Name ⇒ Quarantäne).
- **Komponenten, die NICHT laufen:** `components.hooks` und `components.mcp` sind im Manifest strukturell akzeptiert, aber „reserved — never executed by the current runtime" (PLUGINS.md). Bestätigt durch grep: keine Manifest-Hook-Ausführung in core (die echte Hook-Maschine in `core/user_hooks.py` + Settings-UI ist das *User*-Hook-Feature, nicht das Plugin-Manifest).
- **Der entscheidende Befund:** Ein Plugin kann **keine eigenen Tools registrieren**. `core/plugin_runtime.py` sinngemäß: TOOL_MAP bleibt vollständig, Plugins gaten nur Schema-Ansicht und Ausführung. Kein dynamischer Import von Plugin-Code als Tool. „everything is a plugin" heißt also: Skills/Commands/Agents/Marketplace-Units sind Plugins — die Tools selbst sind built-in.

## 2) Beispiel-Plugins im Repo (beschreibend, BUSL-seitig)
`plugins/` enthält 16 First-Party-Plugins + Signatur-Public-Key: browser-use, **code-shell**, documents, guide, image-studio, local-document-factory, **mcp-connector**, memory, plugin-creator, presentations, private-research-notebook, skill-creator, spreadsheets, vision, voice, web-research.
Lehrreich für uns:
- **code-shell** = exakt unser Muster: Manifest mit `tool_families: [read, write, shell]`, ein Skill-Pack dessen Frontmatter-`allowed_tools` auf built-in Tools zeigen (`run_shell`, `read_file`, `run_tests`, …), Slash-Command `/fix` mit Template; der SKILL.md-Systemprompt choreographiert die built-in Shell zu einem echten Arbeitsablauf (REPRODUCE→FIX→Beweis). Ein Plugin „registriert" seine Fähigkeit also als **Anleitung + Tool-Gating + Slash-Menü**, nicht als Code.
- **mcp-connector** = Beweis, dass MCP in ephe selbst nur ein Plugin ist, das die MCP-Serverliste (`~/.ephe/mcp.json`, Spec-Strings `stdio:…`/`http(s)://…`) verwaltet — MCP ist demnach der *Fallback*, nicht der Königsweg.

## 3) Das „foreman"-Plugin — Spezifikation
**Prinzip:** Da Plugins keine Tools registrieren, sind `hire_job`/`run_bidding_round`/`accept_work`/`board_status` **CLI-Unterkommandos unseres foreman-CLI** (core/foreman_core + scripts/e2e, Apache-seitig fertig), und das Plugin macht sie dem ephe-Agenten als Skill + Slash-Befehle + minimales Tool-Gating benutzbar. Kein ephe-Code, kein ephe-Fork, keine Manifest-Lücke erfunden.

**Installationsort (lokal, außerhalb unseres Repos):** Entwicklungs-Verzeichnis `~/foreman-ephe-plugin/foreman/`, installiert nach `~/.ephe/plugins/foreman/` (ephe-User-Verzeichnis; Repo bleibt BUSL-frei). Auslieferung ans Video-Personal als ZIP mit genau einem Top-Level-Ordner `foreman/` (Install-Konvention: ZIP via Settings oder `ephe plugin install`, Zip-Slip-guarded).

**Layout (~120 Zeilen neu, alles Apache-seitig bei uns, liegt nur ephe-seitig):**
```text
foreman/
├── ephe-plugin.json        # ~25 Zeilen
└── skills/foreman/
    └── SKILL.md            # ~80 Zeilen (Frontmatter + Workflow-Prompt)
```
**ephe-plugin.json (Inhalt):** `manifest_version: 1`, `name: "foreman"`, `version: "0.1.0"`, `description`, `permissions.tool_families: ["read", "shell"]` (minimal; kein network nötig — die Netzwerkeffekte laufen in unserem CLI-Prozess), `data_roots: []`, `components.skills: ["foreman"]`, `components.commands`: `/foreman-hire` (template: „Hire a job with foreman CLI: post '{input}' with budget 3 NEAR-testnet, show the bid board"), `/foreman-board` („run the foreman board and show open jobs with bids"), `/foreman-accept` („accept the delivered work for job {input} and show the receipt + payout state"), `components.agents: []`, keine hooks/mcp-Einträge (reserved → sonst Quarantäne-Risiko bei späterer Verengung).

**SKILL.md (Inhalt):** Frontmatter `trigger: /foreman-hire`, `tools`/`allowed_tools: [run_shell, read_file, list_directory]` (nur reale TOOL_MAP-Namen — code-shell beweist, dass diese Namen existieren), `quality_profile: standard`. System-Prompt-Abschnitt als Workflow-Dogma: 1) `foreman hire "<task>" --budget 3` → erwartet Job-ID + 120-s-Bidding-Fenster nennen; 2) `foreman board <job>` → Bid-Wand (5 Swarms + Dritt-Agent von market.near.ai) zeigen; 3) eine begründete Gegenofferte (`foreman counter <job> --agent <id> --price …`), nie zwei; 4) `foreman accept <job>` → **ohne Signed Receipt (EPHE_CELL_MAP.md, `ExecutionReport.verify` fail-closed) kein Accept**, das dem Agenten als Harte-Gate-Zeile einschreiben; 5) jedes Ergebnis mit `code_hash`/Quote-ID belegen lassen (Haseeb-Regel im Prompt verankern). Approval-Gate der built-in shell bewusst behalten — Mensch klickt „allow" = ehrlichstes Demobild.

**Anbindung an unsere Core-Module:** 1:1 auf bestehenden CLI-Flächen (`core/bidding` Adapter, `core/receipts` nach EPHE_CELL_MAP, `scripts/e2e`); einziger möglicher Zutat-Aufwand: `foreman board --json`-Flag für parsebare Ausgabe (~10 Zeilen, falls der Chat die Tabelle selbst rendern soll — sonst reicht Textausgabe).

## 4) Video-Beweiskraft des K1-Shots
**Shot:** ephe-Chat → `/foreman-hire "build a price-chart PNG from …"` → Approval-Dialog der Shell → Terminal-Panel mit Bid-Wand → Chat-Message mit Receipt-Panel + Payout-Status. Das ist ein **echter** K1-Shot (kein Mock), weil ephe ein reales Produkt mit realem Tool-Loop ist und alle Zahlen aus unserem Contract kommen.
**Notwendig dafür:** laufende ephe-Instanz mit konfiguriertem Engine-Backend (Provider openai_compatible nach `engine.example.json`), Plugin installiert + enabled (`ephe plugin list` zeigt es vor der Kamera), Foreman-CLI auf dem Rechner mit `.env` (Intents-Testnet-Keys, Deploy-Stand), vorbereitete Testnet-Konten + deployter Contract (sonst stirbt der Take in Schritt 1), Bid-Fenster vorher auf kleine Demo-Budgets/120-s gedreht (RULES.md-Konstanten), ein geplanter Fehlversuch als Ehrlichkeit (z. B. `accept` ohne Receipt → sichtbare Ablehnung). **Risiken:** Approval-Dialog muss im Take manuell bestätigt werden (ein Mensch am Rechner nötig — ohnehin Pflicht beim Post); lange Läufe nicht in die built-in shell-Zeit laufen lassen (hire/board asynchron halten — CLI ist nicht-blockend); Quarantäne-Fehler unsichtbar machen (vor dem Take `GET /api/plugins` auf grünen Stand prüfen).

## 5) Plan-Bewertung
- **Plan B — natives Plugin: REALITÄT und Plan A des Projekts.** Beweise: Manifest-Spec mit Enforcement (PLUGINS.md), 16 First-Party-Beispiele inkl. code-shell-Muster, REST-Inspection, ZIP-Install-Pfad, Registry-Enable pro Turn. Einziger ehrlicher Abzug: eigene Tools sind nicht möglich → „Tools" sind CLI-Aufrufe durch built-in `run_shell` (im Video so benennen, nie als „ephe Foreman-Tools" verkaufen).
- **Plan A — MCP: technisch real, aber Fallback.** Es gibt echten MCP-Client-Betrieb (`stdio:…`/`http(s)://…`-Specs, Tool-Namespace `mcp_`, Audit-Events, Lifecycle-Tests mit Crash-Restart/Backoff), verwaltet über das mcp-connector-Plugin bzw. `~/.ephe/mcp.json`/`EPHE_MCP_SERVERS`. Nutzen wir nur, falls der Plugin-Weg im Zeitfenster klemmt: unser Foreman-MCP-stdio-Server (Python, ~80 Zeilen) mit denselben vier Operationen; Manifest-`components.mcp` bleibt tabu (reserved, never executed).
- **Plan C — Terminal-Kulisse: verworfen.** Nicht nötig; und als Judge-Risiko (Haseeb-Test) teurer als jeder Adapter.
