## 1) The plugin subsystem in ephe (evidence state)
- **Documentation:** `docs/PLUGINS.md` (manifest spec v1, enforcement semantics), `docs/PLUGIN_SDK.md` (author entry: create folder → `ephe plugin list` → REST check), `docs/PLUGINS_OVERVIEW.md`, `docs/PLUGIN_PLATFORM_P1/` (platform roadmap), `docs/SKILL_PACKS.md`, `docs/DISCOVER_MARKETPLACE_DESIGN.md`.
- **Code:** `core/plugin_manifest.py` (validation), `core/plugin_store.py`/`plugin_registry.py` (scan/registry), `core/plugin_runtime.py` (gating), `core/plugin_commands.py` (slash menu), `core/plugin_install.py` (ZIP install with zip-slip guard), `core/plugin_listing.py`/`plugin_admin.py` (REST `GET /api/plugins`, `/api/plugins/commands` on :8765), `core/plugin_signing.py` (first-party signatures, key `plugins/first-party.pub.pem`), `core/skills.py` (skill load paths), `core/user_hooks.py` (user hooks, separate from the plugin manifest).
- **Directory/load convention:** plugin = directory `~/.ephe/plugins/<name>/` with mandatory manifest `ephe-plugin.json` (`manifest_version: 1`; `name` = slug = folder name; semver; `permissions.tool_families` ⊆ {read, write, shell, network, memory, vision, docs, browser}; `data_roots` declaration only). Fail-closed: a rule violation quarantines the whole plugin (visible as an error in `GET /api/plugins`); the scan is fail-soft per folder. Enable/disable via the registry takes effect from the next turn — no restart. User skills additionally in `~/.ephe/skills/` (user skills take precedence over built-in `skills/`, deactivation via `skills_state.json`).
- **Components a plugin CAN declare:** `components.skills` (skill packs `skills/<id>/SKILL.md`, agentskills-like frontmatter: name/version/trigger/description/when_to_use/when_not_to_use/tools+allowed_tools/artifact_types + system-prompt section), `components.commands` (`{name, description, template?}` → `/name` in the composer, template expansion server-side), `components.agents` (helper agent profiles, `tools ⊆ TOOL_MAP`, unknown tool name ⇒ quarantine).
- **Components that do NOT run:** `components.hooks` and `components.mcp` are structurally accepted in the manifest but "reserved — never executed by the current runtime" (PLUGINS.md). Confirmed by grep: no manifest-hook execution in core (the real hook machine in `core/user_hooks.py` + settings UI is the *user*-hook feature, not the plugin manifest).
- **The decisive finding:** a plugin can **register no tools of its own**. `core/plugin_runtime.py` in essence: TOOL_MAP stays complete, plugins only gate the schema view and execution. No dynamic import of plugin code as a tool. "everything is a plugin" therefore means: skills/commands/agents/marketplace units are plugins — the tools themselves are built-in.

## 2) Example plugins in the repo (descriptive, BUSL-side)
`plugins/` contains 16 first-party plugins + signature public key: browser-use, **code-shell**, documents, guide, image-studio, local-document-factory, **mcp-connector**, memory, plugin-creator, presentations, private-research-notebook, skill-creator, spreadsheets, vision, voice, web-research.
Instructive for us:
- **code-shell** = exactly our pattern: manifest with `tool_families: [read, write, shell]`, a skill pack whose frontmatter `allowed_tools` point to built-in tools (`run_shell`, `read_file`, `run_tests`, …), slash command `/fix` with a template; the SKILL.md system prompt choreographs the built-in shell into a real workflow (REPRODUCE→FIX→proof). A plugin therefore "registers" its capability as **instructions + tool gating + slash menu**, not as code.
- **mcp-connector** = proof that MCP in ephe itself is only a plugin that manages the MCP server list (`~/.ephe/mcp.json`, spec strings `stdio:…`/`http(s)://…`) — MCP is accordingly the *fallback*, not the royal road.

## 3) The "foreman" plugin — specification
**Principle:** since plugins register no tools, `hire_job`/`run_bidding_round`/`accept_work`/`board_status` are **CLI subcommands of our foreman CLI** (core/foreman_core + scripts/e2e, finished on the Apache side), and the plugin makes them usable to the ephe agent as a skill + slash commands + minimal tool gating. No ephe code, no ephe fork, no invented manifest gap.

**Install location (local, outside our repo):** development directory `~/foreman-ephe-plugin/foreman/`, installed into `~/.ephe/plugins/foreman/` (ephe user directory; the repo stays BUSL-free). Delivery to the video crew as a ZIP with exactly one top-level folder `foreman/` (install convention: ZIP via settings or `ephe plugin install`, zip-slip-guarded).

**Layout (~120 new lines, all Apache-side with us, lives only ephe-side):**
```text
foreman/
├── ephe-plugin.json        # ~25 lines
└── skills/foreman/
    └── SKILL.md            # ~80 lines (frontmatter + workflow prompt)
```
**ephe-plugin.json (content):** `manifest_version: 1`, `name: "foreman"`, `version: "0.1.0"`, `description`, `permissions.tool_families: ["read", "shell"]` (minimal; no network needed — the network effects run in our CLI process), `data_roots: []`, `components.skills: ["foreman"]`, `components.commands`: `/foreman-hire` (template: "Hire a job with foreman CLI: post '{input}' with budget 3 NEAR-testnet, show the bid board"), `/foreman-board` ("run the foreman board and show open jobs with bids"), `/foreman-accept` ("accept the delivered work for job {input} and show the receipt + payout state"), `components.agents: []`, no hooks/mcp entries (reserved → otherwise quarantine risk on later tightening).

**SKILL.md (content):** frontmatter `trigger: /foreman-hire`, `tools`/`allowed_tools: [run_shell, read_file, list_directory]` (only real TOOL_MAP names — code-shell proves these names exist), `quality_profile: standard`. System-prompt section as workflow dogma: 1) `foreman hire "<task>" --budget 3` → expect it to name the job ID + the 120-s bidding window; 2) `foreman board <job>` → show the bid wall (5 swarms + third-party agent from market.near.ai); 3) one reasoned counter-offer (`foreman counter <job> --agent <id> --price …`), never two; 4) `foreman accept <job>` → **no accept without a signed receipt (EPHE_CELL_MAP.md, `ExecutionReport.verify` fail-closed)**, inscribe this as a hard-gate line for the agent; 5) have every result proven with `code_hash`/quote ID (anchor the Haseeb rule in the prompt). Deliberately keep the built-in shell approval gate — a human clicks "allow" = the most honest demo image.

**Connection to our core modules:** 1:1 on existing CLI surfaces (`core/bidding` adapter, `core/receipts` per EPHE_CELL_MAP, `scripts/e2e`); the only possible ingredient effort: a `foreman board --json` flag for parseable output (~10 lines, if the chat should render the table itself — otherwise text output suffices).

## 5) Plan assessment
- **Plan B — native plugin: REALITY and plan A of the project.** Evidence: manifest spec with enforcement (PLUGINS.md), 16 first-party examples incl. the code-shell pattern, REST inspection, ZIP install path, registry enable per turn. The only honest deduction: own tools are not possible → "tools" are CLI calls through built-in `run_shell` (name it that way in the video, never sell it as "ephe Foreman tools").
- **Plan A — MCP: technically real, but a fallback.** There is real MCP client operation (`stdio:…`/`http(s)://…` specs, tool namespace `mcp_`, audit events, lifecycle tests with crash-restart/backoff), managed via the mcp-connector plugin or `~/.ephe/mcp.json`/`EPHE_MCP_SERVERS`. We use it only if the plugin path jams within the time window: our Foreman MCP stdio server (Python, ~80 lines) with the same four operations; manifest `components.mcp` stays taboo (reserved, never executed).
- **Plan C — terminal backdrop: rejected.** Not needed; and as a judge risk (Haseeb test) more expensive than any adapter.
